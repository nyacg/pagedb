Hundred-gigabyte databases in R2, served live by one Durable Object.

The data sits in R2 as immutable 64 KB pages. One object serves it, holding only the pages queries touch. Every view on screen is a live query: when anyone writes, the object works out which rows of which open views changed and pushes just those.       Vector search, in the same pages

      turbopuffer's architecture rebuilt on Durable Objects + R2: an IVF index made of ordinary B+tree pages, next to the rest of the database. Same 1,024-d Qwen3 vectors, benchmarked against turbopuffer and Cloudflare Vectorize.

      turbopuffer is really good: better recall, about 10× faster, real filters, billions of vectors, and someone else runs it. One Durable Object wins on price, live results, and having the vectors sit next to the rest of your data.

      Two stages. The probe tier keeps 1 bit per dimension of each vector's rotated residual (RaBitQ-style, 128 bytes a story), scored with popcounts. The best 100 are rescored with 8-bit codes. Going from 4-bit codes to this took recall from 0.895 to 0.971 at the same page budget.

      One round per stage. The 14,276 centroids are pinned in the object; a search picks the clusters within 256 pages, fetches every missing page at once, then fetches the candidates' 8-bit entries.

      Writes are vectors too. The HN tail embeds each new story (Workers AI, Qwen3) in the same write as its row, so it's searchable on the next search and pushed into open results.

      Where it tops out. The fast tier is the object's 10 GB of SQLite; this index is 7 GB. A small collection (under ~500k vectors) can skip the clusters entirely: all 1-bit codes in memory, brute force, a few ms.

      What it can't do

      • Only queries the app defines. Each list is a named query with an index behind it; a new kind of query means a new index and a rebuild.
      • One object, one thread, one region. No replicas yet: about 7 fresh vector searches a second before they queue, and every read and write goes through one CPU.
      • The base is built offline. 100 GB bases come from a builder in a container. New writes fold into layers in R2 at 4 MB, but rebuilding the base itself is a batch job.
      • 128 MB of memory. The engine's page cache is 40 MiB; everything else pages through SQLite, the city cache or R2. Cold reads from R2 cost ~0.2 s a round.
      • 10 GB of SQLite per object. That's the fast tier. Bigger hot sets need more objects.
      • Vector search trails turbopuffer on recall (0.971 vs 0.990) and speed (138 vs 13 ms), and filters only on columns the index carries.

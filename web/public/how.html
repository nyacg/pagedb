How pagedb works

A database whose base lives in R2 as immutable pages, served by one Durable Object that only ever holds what queries touch. Every list, board column and thread in the tracker is a live query: when anyone writes, the object works out exactly which rows of which open views changed and pushes just those.

Our take on r2db, rebuilt from its public behaviour and built to be measured. The engine is Rust compiled to WebAssembly (the same code builds the dataset natively); the object, sync protocol and UI are TypeScript.

1 · Four tiers, one object

A page is a 64 KiB block of one B+tree. When a query needs a page, it looks in each tier in turn:

2 · A read never waits halfway

The engine can't wait for R2 in the middle of a query (WebAssembly calls are synchronous). So when a query needs a page no synchronous tier holds, it records it and keeps going, collecting every page the query will need, then hands the whole list back. The object fetches them as a few coalesced 1 MiB reads (at most 6 at once, a Durable Object limit) and runs the query again.

  • Interior pages are pinned. Every tree's branch pages and the small tables (users, projects) are built into one contiguous region at the end of the base and loaded when the object starts. Only leaves can be missing.
  • Branch pages know how many rows sit under each child, so a scan for "the newest 50 issues" knows which leaves it will need before reading any of them: one round, however many leaves.
  • Covering indexes. An issue list reads one index that holds whole rows, including the issue's tags and its comment count (kept up to date on every comment). The list for a project touches one or two 64 KiB leaves.
  • Several queries share a round. A board's ten live queries arrive in one message and their missing pages are fetched together.

3 · A write updates the views it affects

Writes don't touch the base. They go into an overlay of index entries in the object's SQLite (durable when acknowledged, like any Durable Object write), and reads merge the base with the overlay. Counts stay instant: each overlay entry carries its effect on the row count.

Each open query is a window of keys. For every write, the engine computes, for each window, which rows enter, leave or change (and refills a window from the index if rows left it). This is done without changing anything: if a page is missing, the whole write is retried once it's fetched, so a push can never half-apply. Then the overlay and every window commit together, and each socket gets one message with its changes.

The tracker applies your edits optimistically: they show instantly, and are reconciled when the server's update (at or after your write's version) arrives. r2db's demo waits for the server.

4 · You can only ask for what the app allows

Every list, column and thread is a named query (issues of a project with these filters; a count; an issue's thread). The page asks the Worker for a lease. The Worker checks the arguments, builds the query and signs it (HMAC, valid for 60 s, bound to this database). The socket subscribes with the lease, and the object only runs a query it can verify it signed. So a visitor can't send a query that scans 100 GB, reads another database, or skips a limit. The first view's leases come inside the HTML, so they cost no extra round trip. Writes work the same way: named mutators, validated by the Worker.

5 · Four apps, one engine

The schema is data: tables, indexes and relations live in each base's manifest. The same engine and the same Durable Object code serve four databases:

  • Hacker News, live: every story and comment since 2006. A small Durable Object tails the HN API and writes new items through the normal write path, so new stories and replies appear in every open tab.
  • r/place 2022: all ~160 million pixel placements. Click a pixel for everyone who ever placed it (an index by pixel); click a user to see all their pixels (an index by user); scrub the timelapse; paint with everyone else.
  • 146 million taxi trips: a spreadsheet you can scroll from the first row to the last. Jumping to row 73,000,000 reads only one path down the tree: branch pages count the rows under each child. Group counts are answered the same way, without reading a row.

6 · Search by meaning, in the same pages

Semantic search on Hacker News runs in the same object as everything else. Every story since 2006 is an embedding (Workers AI, Qwen3-Embedding-0.6B, 1024 dimensions) in a vector index made of ordinary B+trees: one keyed by cluster, story id, whose entries hold a 4-bit code of the story's vector and the columns a result shows, and a small tree of cluster centroids that sits in the pinned region.

  • One round, like every other query. The engine scores the centroids, picks the nearest clusters, finds their leaves through the pinned branch pages and asks for all of them at once. Scoring tens of thousands of vectors is one SIMD dot product each, a few milliseconds.
  • Writes are searchable immediately. A new story and its vector go into the overlay in the same write; searches scan overlay vectors too. A managed vector index (Vectorize) makes writes visible after its next indexing job: seconds to a minute in our measurements.
  • Semantic results are live. A new story that scores into an open search's top results is pushed to every tab showing it, and points and comment counts update in place.
  • It's turbopuffer's shape (object storage as the source of truth, centroids cached, one round trip to object storage per cold query, unindexed writes searched directly) built from Durable Objects, SQLite and R2.

8 · The same object in a container

The database object is ordinary Durable Object code, so it also runs inside workerd in a Cloudflare Container (4 vCPU, 12 GiB). There it gets a 6 GiB page tier instead of 32 MiB and a dedicated CPU. Measured on the 10 GB base: warm queries are the same (~45 ms from a laptop), and fan-out to 1,000 sockets is about twice as fast (write → every tab: p50 128 ms vs 255 ms; p99 296 ms vs 684 ms). The trade-offs: a container takes at most 4,096 connections, its cold start takes seconds, and it reaches R2 through a bridge.

9 · Limits (honest list)

  • Only indexed queries. A query must be answerable from an index (equalities, then the index order); anything else is refused rather than scanning 100 GB.
  • One object's CPU. All reads, writes and pushes for a database run on one thread. Read replicas (more objects sharing the base) are the next step.
  • Cold reads cost R2 latency (~200 ms+ per round for parts nobody has read recently).
  • Base data is generated and users/projects are read-only in the demo; the activity feed's index holds the newest 500k comments of the base plus everything written since.

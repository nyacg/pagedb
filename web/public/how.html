How pagedb works

A database whose base lives in R2 as immutable pages, served by one Durable Object that only ever holds what queries touch. Every list, board column and thread in the tracker is a live query: when anyone writes, the object works out exactly which rows of which open views changed and pushes just those.

Our take on r2db, rebuilt from its public behaviour and built to be measured. The engine is Rust compiled to WebAssembly (the same code builds the dataset natively); the object, sync protocol and UI are TypeScript.

1 · Four tiers, one object

A page is a 64 KiB block of one B+tree. When a query needs a page, it looks in each tier in turn:

2 · A read never waits halfway

The engine can't wait for R2 in the middle of a query (WebAssembly calls are synchronous). So when a query needs a page no synchronous tier holds, it records it and keeps going, collecting every page the query will need, then hands the whole list back. The object fetches them as a few coalesced 1 MiB reads (at most 6 at once, a Durable Object limit) and runs the query again.

  • Interior pages are pinned. Every tree's branch pages and the small tables (users, projects) are built into one contiguous region at the end of the base and loaded when the object starts. Only leaves can be missing.
  • Branch pages know how many rows sit under each child, so a scan for "the newest 50 issues" knows which leaves it will need before reading any of them: one round, however many leaves.
  • Covering indexes. An issue list reads one index that holds whole rows, including the issue's tags and its comment count (kept up to date on every comment). The list for a project touches one or two 64 KiB leaves.
  • Several queries share a round. A board's ten live queries arrive in one message and their missing pages are fetched together.

3 · A write updates the views it affects

Writes don't touch the base. They go into an overlay of index entries in the object's SQLite (durable when acknowledged, like any Durable Object write), and reads merge the base with the overlay. Counts stay instant: each overlay entry carries its effect on the row count.

Each open query is a window of keys. For every write, the engine computes, for each window, which rows enter, leave or change (and refills a window from the index if rows left it). This is done without changing anything: if a page is missing, the whole write is retried once it's fetched, so a push can never half-apply. Then the overlay and every window commit together, and each socket gets one message with its changes.

The tracker applies your edits optimistically: they show instantly, and are reconciled when the server's update (at or after your write's version) arrives. r2db's demo waits for the server.

5 · Limits (honest list)

  • Only indexed queries. A query must be answerable from an index (equalities, then the index order); anything else is refused rather than scanning 100 GB.
  • One object's CPU. All reads, writes and pushes for a database run on one thread. Read replicas (more objects sharing the base) are the next step.
  • Cold reads cost R2 latency (~200 ms+ per round for parts nobody has read recently).
  • Base data is generated and users/projects are read-only in the demo; the activity feed's index holds the newest 500k comments of the base plus everything written since.
